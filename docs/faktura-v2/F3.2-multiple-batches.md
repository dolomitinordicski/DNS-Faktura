# DNS Faktura v2 — F3.2 Multiple Batches & Remaining Quantities

## Goal

An Order may have multiple Confirmation Batches, but confirmed quantities must never overlap.

For each OrderLine:

remainingConfirmableQuantity =
orderedQuantity - sum(confirmed quantities from prior CONFIRMED batches)

Only CONFIRMED batches consume quantity.

DRAFT, SENT and CHANGE_REQUESTED batches do not consume the quantity until they become CONFIRMED.

## Rules

1. A new confirmation batch proposes only the still-unconfirmed remainder.
2. If remainingConfirmableQuantity is zero, that OrderLine cannot be added to another confirmation.
3. Before confirming a batch, requested/confirmed quantities must be checked against the current remaining quantity.
4. Parallel/open batches may exist, but the later confirmation must fail/review if another batch has consumed part of the same quantity in the meantime.
5. Historical Order.orderedQuantity remains unchanged.
6. The engine never silently reallocates quantities between batches.

## Example

Order wristbands = 500.

Confirmation A confirms 300.

Remaining = 200.

Confirmation B for the same OrderLine may propose at most 200.

If B proposes 250:
CONFIRMATION_EXCEEDS_REMAINING.

If A = 300 and B = 200 are confirmed:
remaining = 0 and a third batch is rejected.

## Concurrency principle

The remaining-quantity check must be repeated at persistence/commit time once Firebase adapters are introduced. Domain validation alone is not sufficient against two simultaneous writes.
