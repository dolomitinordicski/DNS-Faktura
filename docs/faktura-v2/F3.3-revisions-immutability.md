# DNS Faktura v2 — F3.3 Revisions & Immutability

## Principle

A CONFIRMED confirmation is never edited in place.

Corrections produce a new confirmation object with:
- a new id
- revision = previous revision + 1
- supersedesConfirmationId
- an explicit reason

The original keeps its original lines, quantities, actor and confirmation timestamp.

## Two lifecycle operations

### Void

Use when the confirmed document must be cancelled without replacement.

CONFIRMED -> VOIDED

Required audit data:
- voidedAt
- voidedBy
- reason

VOIDED confirmations no longer consume confirmable quantity.

### Replace / correct

Use when a confirmed document must be corrected.

1. create correction revision from CONFIRMED original
2. new revision starts as DRAFT
3. normal SENT / CHANGE_REQUESTED workflow applies
4. DNS approval performs one atomic replacement transaction:
   - replacement CHANGE_REQUESTED -> CONFIRMED
   - original CONFIRMED -> SUPERSEDED
   - original records supersededByConfirmationId
   - replacement records supersedesConfirmationId
   - quantity ledger is swapped from original quantities to replacement quantities
   - confirmation + supersede audit events are appended atomically

There is no persisted intermediate state where both original and replacement are active CONFIRMED confirmations.

SUPERSEDED confirmations no longer consume confirmable quantity; the active replacement does.

## Example

Order = 500 wristbands.

Confirmation C1 rev.1 confirms 300.

A correction is required:
- C2 rev.2 is created from C1
- area/DNS confirms 250
- C1 becomes SUPERSEDED
- C2 remains CONFIRMED

Effective confirmed quantity = 250.
Remaining confirmable quantity = 250.

The historical value 300 remains visible in C1 and is never overwritten.

## Concurrency / persistence rule

Replacement approval is persisted transactionally in one operation:
- verify original is still CONFIRMED
- verify replacement is still CHANGE_REQUESTED
- verify lineage/revision/scope
- validate current order-line quantities and ledger
- compute ledger as current - original + replacement
- write original SUPERSEDED + replacement CONFIRMED together
- append both audit events in the same transaction

## Billing consequence

A correction to a confirmation does not silently rewrite a READY or INVOICED billing snapshot.

Billing revision handling is a separate guard and will be defined in the next billing immutability phase.
