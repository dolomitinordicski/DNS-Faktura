# DNS Faktura v2 — F3.8 Audit / Event Model

## Principle

Important business transitions produce append-only Domain Events.

Events explain what happened without reconstructing history from mutable documents.

## Event families

Confirmation:
- CONFIRMATION_CREATED
- CONFIRMATION_SENT
- CONFIRMATION_CHANGE_REQUESTED
- CONFIRMATION_CONFIRMED
- CONFIRMATION_SUPERSEDED
- CONFIRMATION_VOIDED

Billing:
- BILLING_READY
- BILLING_INVOICED

Payment:
- PAYMENT_MARKED_OPEN
- PAYMENT_MARKED_PAID

Delivery:
- DELIVERY_CREATED
- DELIVERY_UPDATED
- DELIVERY_COMPLETED

## Required event metadata

Every event records:
- unique event id
- event type
- timestamp
- actor id
- optional actor label
- season
- organization
- entity type
- entity id
- optional entity revision
- structured payload

## Rules

1. events are append-only
2. event ids are unique
3. event history is chronological
4. events do not replace domain objects; they audit their transitions
5. later persistence must prevent update/delete of historical events except exceptional administrative repair outside normal application flow

## Privacy

Audit payloads should contain only data needed to explain the business action. Confirmation acceptance data and any personal details require a separate retention/privacy policy before persistence is implemented.
