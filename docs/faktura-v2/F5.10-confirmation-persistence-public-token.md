# DNS Faktura v2 — F5.10 Confirmation Persistence & Public Tokens

## Scope

F5.10 implements real Faktura-owned persistence for Confirmation revisions and the public confirmation token flow.

Collections:
- `fakturaConfirmations`
- `fakturaConfirmationTokens`
- `fakturaConfirmationLedgers`
- `fakturaEvents`

No UI/Foundation dependency is introduced.

## Confirmation persistence

`FirestoreConfirmationRepository` implements:
- getById
- listActiveByOrder
- createDraft
- confirmTransaction
- finalizeReplacementTransaction

Creation writes:
- Confirmation DRAFT
- CONFIRMATION_CREATED audit event

Frozen lifecycle states remain immutable business snapshots except for explicit lifecycle transitions such as SUPERSEDED.

## Public dispatch

DRAFT -> SENT and public-token creation happen in one Firestore transaction.

The token document contains:
- id
- confirmationId
- tokenHash
- active
- createdAt
- expiresAt?
- usedAt?
- revokedAt?

The raw token is never persisted.

The application service generates 32 random bytes and returns the raw token once for URL construction.

Firestore stores SHA-256 only.

## Public response

The public client supplies:
- raw token
- requested quantities
- actor label/name
- response timestamp

The application hashes the raw token and the persistence layer resolves the matching token record.

The token is one-shot:
- successful response sets active=false and usedAt
- reused or revoked tokens are rejected
- expired tokens are rejected

## Quantity ledger

`fakturaConfirmationLedgers/{orderId}` stores transactionally consumed quantities:

`confirmedByLine[orderLineId] = confirmed quantity currently active`

Purpose:
- prevent two concurrent Confirmation batches from consuming the same remaining quantity
- avoid trusting client-side remaining-quantity calculations
- support correction/replacement revisions atomically

### Unchanged public response

If all requested quantities equal the proposed quantities:
- Confirmation -> CONFIRMED
- ledger quantities increment atomically
- token is consumed
- CONFIRMATION_CONFIRMED audit event is appended

### Changed public response

If at least one quantity differs:
- whole Confirmation -> CHANGE_REQUESTED
- all requested quantities are preserved
- no ledger quantity is consumed yet
- token is consumed
- CONFIRMATION_CHANGE_REQUESTED audit event is appended

DNS approval later performs the transactional quantity validation and only then moves to CONFIRMED.

## Correction / replacement

A correction revision may reference `supersedesConfirmationId`.

During DNS approval:
- remaining quantity is checked as if the original active quantity were temporarily released
- the replacement can reach CONFIRMED candidate state without double-consuming the ledger

During final replacement:
- original CONFIRMED -> SUPERSEDED
- replacement remains CONFIRMED
- ledger subtracts original quantities and adds replacement quantities
- current Data Entry order-line quantities are reread and revalidated inside the same transaction
- CONFIRMATION_SUPERSEDED audit event is written atomically

This protects against another batch consuming quantity between correction approval and replacement finalization.

## Multi-line response rule

Confirmation response evaluation is batch-wide and order-independent.

If any line changes:
- entire batch becomes CHANGE_REQUESTED
- every line stores requestedQuantity
- no line receives confirmedQuantity

If no line changes:
- entire batch becomes CONFIRMED
- every line receives confirmedQuantity

## Security boundary

Public clients never query `fakturaConfirmations` directly by arbitrary document id.

Access is mediated by a separate random token whose hash is stored server-side.

The token flow provides scoped application access only; it is not a qualified digital signature.
