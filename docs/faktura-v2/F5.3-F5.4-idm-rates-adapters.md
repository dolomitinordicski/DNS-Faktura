# DNS Faktura v2 — F5.3 / F5.4 IDM & Commercial Rate Adapters

## F5.3 IDM

Current source state:

- allocation keys are real/canonical records in DNS Core collection `areaAllocationKeys`
- the 2026/27 IDM Premiumpartner program definition is still legacy configuration from Faktura v1
- no canonical shared IDM program record was found yet

The v2 adapter therefore separates:

1. program configuration
   - season
   - amount per reporting area
   - participating reporting areas
   - source label
   - program revision

2. allocation backend
   - reads active `areaAllocationKeys` from DNS Core
   - maps organizationId -> share
   - preserves allocation revision

Organization charge:

amount = amountPerReportingArea * organization share

Faktura does not own or edit allocation keys.

When IDM program data is moved to a governed canonical source, only `loadProgram()` changes. Domain contracts remain unchanged.

## F5.4 Commercial Rates

Real source:
- DNS Core / `billingRateConfigs`

Adapter reads:
- sourceType = order
- catalogItemId
- billingUnitPrice
- revision
- active
- source.documentLabel
- prepaymentRequired when present

The adapter returns the highest active revision for the requested catalog item.

### Legacy prepayment compatibility

Existing v1 rate documents do not consistently contain `prepaymentRequired`.

For migrated physical order rates, the Firebase backend currently uses:

`prepaymentRequired = true`

when the field is absent.

This is a compatibility default reflecting the operational rule that DNS generally advances material costs before delivery.

It is not hard-coded in the domain engine. Once the field is explicitly governed in the rate source, that source value takes precedence.

## Architecture

Firebase/DNS Core
-> FirebaseIdmBackend / FirebaseCatalogPriceBackend
-> IdmAdapter / CatalogPriceAdapter
-> IdmChargeSource / CatalogPriceSource
-> v2 domain

No UI or Foundation dependency is introduced.
