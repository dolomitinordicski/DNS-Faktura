# DNS Faktura v2 — F5.5 Billing Draft Orchestrator

## Purpose

The application orchestrator builds one Faktura v2 DRAFT BillingSheet for one organization and one season.

It does not write to Firebase and does not depend on UI/Foundation.

## Inputs

- submitted Orders from DNS Data Entry / DNS Core
- confirmed Faktura Confirmation objects
- FAIR contribution source
- IDM charge source
- catalog commercial rates

## Assembly rules

### FAIR
When a FAIR result exists for the organization, add one flat FAIR line using the published amount and source revision.

### IDM
When an IDM charge exists for the organization, add one flat IDM line using the governed allocation result returned by the IDM adapter.

### Orders
Raw order quantities are never billed directly.

A material billing line exists only when:
1. the Confirmation belongs to the same season/organization
2. Confirmation status is CONFIRMED
3. its original submitted Order can be resolved
4. every confirmed catalog item has an active commercial rate

The billed quantity is confirmedQuantity.

## Missing rates

No price is invented.

If one confirmed item has no commercial rate:
- the confirmation's material lines are not added to the BillingSheet
- the orchestrator returns a MISSING_RATE issue
- the Draft remains incomplete for later resolution

## Lineage

Material BillingLines freeze both independent lineages:

- sourceId/sourceRevision = Confirmation id/revision
- rateId/rateRevision = commercial rate id/revision

This is necessary because a quantity confirmation and a commercial price can evolve independently.

## Output

BillingAssemblyResult contains:
- DRAFT BillingSheet
- current source revision snapshots
- Confirmation readiness snapshots
- assembly issues/blockers

This becomes the input for the existing F3.6 readiness engine before transition to READY.
