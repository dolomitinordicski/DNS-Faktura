# DNS Faktura v2 — F5.6 Application Readiness Gate

## Purpose

F5.6 connects the F5.5 Billing Draft orchestrator to the existing F3.6 readiness engine.

A DRAFT can move to READY only when both application assembly and domain readiness are clean.

## Why a separate application gate is required

The domain readiness engine validates the lines already present in the BillingSheet.

The orchestrator can also detect problems before a line is created, for example:
- a confirmed catalog item has no commercial rate
- a Confirmation belongs to another organization
- the original Order cannot be resolved

Those blockers must not disappear merely because the affected line was omitted from the Draft.

## Readiness layers

1. Assembly blockers
   - CONFIRMATION_SCOPE_MISMATCH
   - CONFIRMATION_ORDER_NOT_FOUND
   - CONFIRMATION_NOT_CONFIRMED
   - MISSING_RATE

2. Domain readiness
   - required source types
   - source freshness
   - Confirmation revision/status
   - valid quantity/unit price/amount

3. Commercial rate freshness
   - material lines must contain rateId and rateRevision
   - current active rate must still exist
   - a newer rate revision blocks READY
   - same revision with another rateId blocks READY

## Policy

requiredSourceTypes remains an explicit caller policy.

FAIR or IDM are not globally mandatory because applicability varies by organization and season.

## Transition

`markAssembledBillingReady()`:
- accepts only DRAFT
- evaluates all three layers
- throws BILLING_NOT_READY with issue codes if any blocker exists
- otherwise returns a READY BillingSheet

No persistence or UI dependency is introduced.
