# DNS Faktura v2 — F5.8 Invoicing & PaymentCase

## Scope

F5.8 connects the READY BillingSheet to operational invoicing state and PaymentCase tracking.

It does not issue fiscal invoices and does not implement accounting or bank reconciliation.

## Atomic READY -> INVOICED

`invoiceBillingAndOpenPayment()` uses one Firestore transaction.

The transaction:
1. reads the READY BillingSheet
2. verifies no PaymentCase already exists
3. writes BillingSheet -> INVOICED
4. creates one PaymentCase with status OPEN
5. writes BILLING_INVOICED audit event
6. writes PAYMENT_MARKED_OPEN audit event

All writes succeed or fail together.

## PaymentCase semantics

PaymentCase is operational only.

Fields:
- billingSheetId
- required
- status OPEN | PAID
- paidAt?
- reference?
- updatedAt
- updatedBy

`required` means:

**payment/prepayment is required before physical delivery may be released**

It does not mean that a non-required invoice is free or does not need to be settled.

The flag is derived from invoiced physical order lines where:
- sourceType = ORDER_CONFIRMATION
- quantity > 0
- prepaymentRequired = true

## Mark PAID

`markPaymentPaid()`:
- requires an INVOICED BillingSheet
- requires an existing PaymentCase
- changes OPEN -> PAID
- stores paidAt/reference
- writes PAYMENT_MARKED_PAID in the same transaction

A PAID case cannot be reopened by the current v2 model.

Repeated PAID calls with the same reference are idempotent at the domain level; conflicting references are rejected.

## Delivery relationship

F3.7 remains authoritative:
- INVOICED is required for delivery
- if PaymentCase.required/prepayment applies, payment must be PAID before release
- non-prepayment material may be released after invoicing even while PaymentCase is OPEN

## Collections

- fakturaBillingSheets
- fakturaPayments
- fakturaEvents

No UI/Foundation dependency is introduced.
