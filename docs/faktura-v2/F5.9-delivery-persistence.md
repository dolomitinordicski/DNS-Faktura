# DNS Faktura v2 — F5.9 Delivery Persistence

## Scope

F5.9 closes the operational chain from an INVOICED BillingSheet and its PaymentCase to physical delivery tracking.

No UI/Foundation dependency is introduced.

## Important correction: delivery is order-scoped

A BillingSheet may contain material lines from multiple Orders.

Therefore a Delivery record must never take every material line from the BillingSheet blindly.

Each material BillingLine now freezes:
- Confirmation source id/revision
- catalog item
- commercial rate lineage
- **orderId**

`createDeliveryFromBilling()` selects only material lines whose `orderId` matches the Delivery order.

## Release rules

Delivery creation requires:
- BillingSheet = INVOICED
- exact PaymentCase linkage
- at least one material line for the selected order
- PAID when any selected deliverable line requires prepayment

FAIR, IDM and manual/service lines are never deliverable.

## Firestore transaction

`FirestoreDeliveryRepository.createTransaction()` rereads:
- fakturaBillingSheets/{billingSheetId}
- fakturaPayments/{billingSheetId}

It reconstructs the expected Delivery snapshot from current persisted state and rejects any mismatch.

Atomic writes:
- fakturaDeliveries/{deliveryId}
- DELIVERY_CREATED audit event

## Partial / complete delivery

`recordQuantityTransaction()`:
- reads current Delivery
- validates deliveredQuantity <= confirmedQuantity
- updates deliveredQuantity / remainingQuantity
- derives PENDING / PARTIAL / DELIVERED
- writes DELIVERY_UPDATED or DELIVERY_COMPLETED audit event atomically

Delivery quantities are cumulative absolute quantities, not increments.

## Safety

CI uses in-memory repository doubles.
No production Delivery records are created by the test workflow.
