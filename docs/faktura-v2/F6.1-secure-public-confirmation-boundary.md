# DNS Faktura v2 — F6.1 Secure Public Confirmation Boundary

## Status

Implementation complete in code.

Activation requires:
1. merge/deploy canonical DNS Core rules from `dns-shared-data` PR #149
2. deploy the Faktura public Functions from this repository
3. configure the future public UI with the deployed Functions base URL

No automatic production deployment is enabled by this phase.

## Security architecture

Public browsers do **not** read or write Faktura Firestore collections directly.

Flow:

`public browser -> HTTPS Function -> Firebase Admin SDK -> Faktura collections`

The Functions are:
- `resolvePublicConfirmation`
- `submitPublicConfirmation`

Both run in `europe-west1`.

## Token handling

Internal DNS dispatch:
- generates 32 random bytes
- returns the raw token once for URL construction
- stores only SHA-256 in `fakturaConfirmationTokens`

Public request:
- sends raw token over HTTPS
- server hashes token
- server performs token lookup using Admin SDK
- Firestore client rules never expose the token collection

Token checks:
- active
- not used
- not revoked
- not expired

Expiry uses **server current time**, never a caller-provided timestamp.

## Public resolve payload

The resolve endpoint returns only:
- confirmationId
- acceptanceTextVersion
- orderLineId
- catalogItemId
- proposedQuantity
- unit

It does not expose:
- token hashes
- ledger data
- billing state
- payment data
- audit data
- other Confirmations

## Public submit

The submit endpoint accepts:
- raw token
- requested quantities
- human actor label

It derives server-side:
- timestamp
- audit actor principal
- expiry state
- quantity consumption

The audit principal is:

`public-confirmation-token:{tokenId}`

The submitted human name remains `actorLabel` / `confirmedBy`, not an authenticated identity.

## Concurrency

For unchanged responses:
- current token is re-read inside transaction
- current Confirmation is re-read
- current quantity ledger is re-read
- Data Entry order lines are re-read
- remaining quantity is revalidated
- ledger + Confirmation + consumed token + audit event commit atomically

For changed responses:
- Confirmation becomes CHANGE_REQUESTED
- token is consumed
- no quantity is consumed yet

## Firestore rules

Canonical rules live in:

`dolomitinordicski/dns-shared-data/firestore.rules`

F6.1 rules branch/PR:

`faktura-v2-security-boundary` / PR #149

The following collections are restricted to active `dns-admin` clients:
- fakturaConfirmations
- fakturaBillingSheets
- fakturaPayments
- fakturaDeliveries
- fakturaManualSources
- fakturaConfirmationTokens
- fakturaConfirmationLedgers

`fakturaEvents`:
- admin read
- admin create
- no client update/delete

Anonymous and non-admin clients have no direct access.

Server-side Functions use Firebase Admin and enforce the public capability-token policy themselves.

## Deployment

Functions deployment is intentionally manual:

`.github/workflows/deploy-faktura-functions.yml`

It requires repository secret:

`FIREBASE_SERVICE_ACCOUNT_DNS_CORE`

The workflow:
- authenticates to Google
- installs isolated Functions dependencies
- validates syntax
- deploys only Functions to `dns-core`

It does not deploy Firestore rules or GitHub Pages.

## CI

The v2 scenario workflow now also:
- installs the isolated Functions package
- validates `functions/src/index.mjs` syntax

Canonical rules are tested with the DNS Core Firestore emulator in `dns-shared-data`.

## Additional F6 fix discovered here

Firestore requires transaction reads before writes.

F6.1 found and corrected a latent ordering error in Confirmation approval and the new public response transaction:
- all ledger/order/event reads now happen before any `transaction.set()`
- writes occur only after all required reads complete

## Remaining security hardening

Before public launch:
- verify production Functions IAM allows invocation as intended
- connect public UI only to HTTPS Functions
- consider Firebase App Check once the public UI exists
- consider platform-level throttling/rate limiting if abuse becomes material
- never add direct public Firestore permissions for Faktura token/Confirmation collections
