# DNS Faktura v2 — F6.2 Live READY Freshness

## Purpose

F6.2 closes the READY freshness gap identified by F6.

A BillingSheet may move from DRAFT to READY only after its persisted DRAFT is revalidated against the current live upstream sources.

The canonical path is now:

persisted DRAFT
-> live source re-read
-> readiness evaluation
-> local Firestore transaction revalidation
-> READY

## Why this exists

Assembly-time snapshots are not enough.

Between DRAFT creation and READY:
- FAIR may publish a new revision
- IDM allocation may change
- a Confirmation may be revised/superseded
- a commercial rate may change
- a caller may hold an old in-memory BillingSheet

F6.2 removes reliance on those stale in-memory snapshots.

## Persisted DRAFT is authoritative

`persistBillingReady()` first reloads the BillingSheet from its repository.

It verifies:
- document exists
- status = DRAFT
- persisted `updatedAt` equals `expectedUpdatedAt`

Live readiness is evaluated against that persisted BillingSheet, not against a caller-owned copy.

The final Firestore transaction repeats the same `updatedAt` guard, preventing the DRAFT from changing between preflight and commit.

## Live preflight sources

### FAIR

When FAIR is present in the BillingSheet or required by policy:
- read current contribution
- compare sourceId
- compare revision
- compare amount when revision is unchanged

A newer revision blocks READY.
A rollback/lower revision also blocks READY.
A same-revision value mutation blocks READY.

FAIR lives in a separate Firebase project, therefore it cannot be included in the DNS Core Firestore READY transaction.

Accepted consistency model:
- FAIR revisions are treated as immutable published snapshots
- FAIR is reread immediately before READY
- exact revision is frozen on the BillingLine
- later FAIR revisions require a new BillingSheet revision
- the persisted DRAFT is protected from changing after that check by `expectedUpdatedAt`

### IDM

When IDM is present or required:
- reread current program/allocation through the IDM adapter
- compare source id/revision
- compare amount when revision is unchanged

Inside the DNS Core READY transaction, the current `areaAllocationKeys/{seasonId}-{reportingAreaId}` record is also reread.

A newer local allocation revision blocks the transaction.

The 2026/27 program definition remains transitional configuration and is tracked separately by F6-H02.

### Confirmations

Every material BillingLine causes its current Confirmation to be reread.

Preflight validates:
- exists
- status = CONFIRMED
- exact revision
- orderId
- catalog item
- confirmed quantity

Inside the READY Firestore transaction the same Confirmation documents are reread and validated again against the frozen BillingLines.

### Commercial rates

Every material BillingLine rereads its current active rate.

Preflight validates:
- current active rate exists
- exact rateId/revision
- unitPrice
- prepaymentRequired

A newer rate revision blocks READY.
A lower/rollback revision blocks READY.
A same-revision value mutation blocks READY.

Inside the READY transaction, `billingRateConfigs/{rateId}` is reread and validated again.

## Applicability

FAIR and IDM are loaded only if:
- a corresponding line exists in the BillingSheet, or
- the caller policy lists the source type in `requiredSourceTypes`

This avoids blocking organizations for sources that do not apply to them.

## Transaction boundary

DNS-Core-local checks performed again inside READY transaction:
- persisted BillingSheet version
- Confirmations
- commercial rates
- IDM allocation record
- duplicate READY audit event

FAIR is cross-project and remains the only source that cannot join the DNS Core transaction.

## New application issue codes

F6.2 adds:
- SOURCE_REVISION_MISMATCH
- SOURCE_VALUE_MISMATCH
- RATE_REVISION_MISMATCH
- RATE_VALUE_MISMATCH

Existing codes such as:
- STALE_SOURCE
- MISSING_SOURCE
- CONFIRMATION_REVISION_MISMATCH
- STALE_RATE
- MISSING_CURRENT_RATE

remain valid.

## Result

After F6.2, the canonical persisted READY path no longer trusts assembly-time source snapshots.

Remaining critical backend blocker from the F6 audit:
- F6-B04 correction replacement intermediate double-active state

Recommended next phase:
- F6.3 atomic correction replacement
