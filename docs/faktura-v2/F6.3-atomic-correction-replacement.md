# DNS Faktura v2 — F6.3 Atomic Correction Replacement

## Purpose

F6.3 removes the last critical Confirmation lifecycle race identified by the F6 audit.

Before F6.3 a correction could be approved in two steps:

1. replacement CHANGE_REQUESTED -> CONFIRMED
2. original CONFIRMED -> SUPERSEDED

That created a short but real state where both original and replacement were active CONFIRMED records.

F6.3 removes that state entirely.

## Canonical replacement approval

For a Confirmation with `supersedesConfirmationId`, `ConfirmationRepository.confirmTransaction()` now performs one Firestore transaction that:

1. reads the replacement
2. reads the original
3. verifies replacement = CHANGE_REQUESTED
4. verifies original = CONFIRMED
5. verifies exact lineage, revision and scope
6. reads current quantity ledger
7. rereads every affected Data Entry order line
8. computes:
   `nextLedger = currentLedger - originalQuantity + replacementQuantity`
9. rejects negative ledger values
10. rejects quantities beyond current ordered quantity
11. transforms replacement -> CONFIRMED
12. transforms original -> SUPERSEDED
13. writes both Confirmation records
14. writes the updated quantity ledger
15. writes CONFIRMATION_CONFIRMED for the replacement
16. writes CONFIRMATION_SUPERSEDED for the original

All writes commit or fail together.

## Removed path

`finalizeReplacementTransaction()` has been removed from the persistence contract and repository.

There is no supported two-phase persistence API anymore.

## Domain transition

`approveReplacementRevisionAtomically()` expresses the paired final state:

Input:
- original CONFIRMED
- replacement CHANGE_REQUESTED

Output:
- original SUPERSEDED
- replacement CONFIRMED

The helper also validates:
- supersedesConfirmationId
- sequential revision
- season
- organization
- order

## Non-replacement confirmations

Ordinary CHANGE_REQUESTED confirmations with no `supersedesConfirmationId` still use the normal approval transaction:
- validate current ledger/order quantities
- move to CONFIRMED
- consume quantity
- append CONFIRMATION_CONFIRMED event

## Ledger invariant

At no point during correction approval does the ledger count both original and replacement.

For each affected order line:

`next = current - original + replacement`

This keeps the effective confirmed quantity stable and race-safe.

## Result

After F6.3:
- no double-active Confirmation window exists in the canonical persistence path
- listActiveByOrder cannot observe both original and approved replacement as CONFIRMED due to an intermediate application state
- billing live-readiness can rely on the persisted active Confirmation set
- the old finalize persistence API no longer exists

This closes F6-B04 from the backend audit.
