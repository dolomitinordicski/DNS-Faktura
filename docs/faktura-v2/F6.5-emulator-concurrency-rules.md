# DNS Faktura v2 — F6.5 Emulator, Concurrency & Rules Integration

## Purpose

F6.5 validates the Faktura v2 persistence model against real Firebase emulators.

The previous scenario suite remains valuable for fast domain regression tests, but it cannot prove Firestore transaction retry behavior, concurrent writes, Functions one-shot behavior or deployed security-rule semantics.

F6.5 adds those checks.

## Test layers

### 1. Faktura domain scenarios

Existing in-memory scenarios remain the fast first layer.

They validate:
- domain transitions
- application orchestration
- readiness logic
- persistence contracts
- state invariants

### 2. DNS-Faktura Firestore + Functions Emulator

New integration suite:

`src/v2/tests/firestoreIntegration.ts`

Runs against:
- Firestore Emulator on port 8089
- Functions Emulator on port 5002
- project `demo-dns-core`

Configuration:

`firebase.integration.json`

The integration rules file:

`tests/firestore.integration.rules`

is deliberately permissive and TEST-ONLY.

Its purpose is to test repository and transaction semantics without duplicating production authorization rules.

Canonical production rules remain exclusively in `dns-shared-data`.

## Emulator integration scenarios

### Concurrent confirmation quantity consumption

Two CHANGE_REQUESTED Confirmations concurrently attempt to consume 400 units from one 500-unit order line.

Expected:
- exactly one transaction succeeds
- exactly one transaction fails with CONFIRMATION_EXCEEDS_REMAINING
- ledger total = 400
- exactly one Confirmation is active CONFIRMED

This proves Firestore transaction retry protects the quantity ledger.

### Atomic replacement concurrency

Two concurrent approval calls target the same correction replacement.

Expected:
- one succeeds
- one retries and fails because the replacement is no longer CHANGE_REQUESTED
- original = SUPERSEDED
- replacement = CONFIRMED
- ledger reflects only replacement quantity
- CONFIRMATION_CONFIRMED event exists once
- CONFIRMATION_SUPERSEDED event exists once

### Concurrent MANUAL_SERVICE DRAFT mutation

Two operators mutate the same DRAFT with the same expectedUpdatedAt.

Expected:
- one succeeds
- the retry sees updatedAt changed
- one fails with BILLING_DRAFT_CHANGED
- only one manual line affects totalAmount
- one audit event is written

### READY source guard + duplicate transition

The integration suite first changes a commercial rate after DRAFT creation.

Expected:
- READY transaction is rejected with READY_RATE_CHANGED

Then the exact frozen rate is restored and two READY transitions race.

Expected:
- one succeeds
- one fails after transaction retry because the BillingSheet is no longer DRAFT
- final status = READY
- BILLING_READY event exists once

### Public confirmation token one-shot concurrency

Two HTTP requests simultaneously call the actual Functions Emulator endpoint:

`submitPublicConfirmation`

with the same raw token.

Expected:
- one HTTP 200
- one HTTP 410
- token active = false
- usedAt exists
- Confirmation = CONFIRMED
- ledger quantity consumed exactly once
- one CONFIRMATION_CONFIRMED audit event

This validates the complete server-side F6.1 boundary under concurrency, not merely a mocked handler.

## Canonical rules tests

Production DNS Core rules remain in:

`dolomitinordicski/dns-shared-data`

Current Faktura security PR:

**#149 — F6.1/F6.5 secure DNS Faktura v2 Firestore collections**

The rules suite verifies:
- Faktura internal collections are DNS-admin only
- non-admin users cannot read/write BillingSheet, Payment or Delivery state
- token documents cannot be read directly by non-admin clients
- tokenHash queries are denied to non-admin and anonymous clients
- quantity ledger is internal
- Faktura events are append-only
- anonymous users cannot enumerate the token collection

The rules tests use `@firebase/rules-unit-testing` against the canonical Firestore rules.
